## 1. 설명의 중심

### 한 문장 정의

실험플랫폼 인프라는 서비스가 클라우드에서 운영될 수 있도록 외부 요청과 데이터 저장소를 연결하고, 새 버전 배포와 운영 상태 확인을 자동화합니다.

### 핵심 차별점

“어떤 클라우드 기술을 사용했는가”보다 **“코드부터 운영 상태까지 어떻게 일관되게 이어지는가”**가 중요합니다.

- 외부 요청은 안전한 접속 처리 후 하나의 실험플랫폼 서비스로 전달됩니다.
- 실험 설정·노출 기록·대상 판단 데이터는 용도별 저장소에 보관합니다.
- 코드 변경은 자동 검사를 통과한 뒤 실행 가능한 이미지로 만들어집니다.
- 운영 저장소의 버전 정보가 바뀌면 배포 도구가 새 버전을 자동 반영합니다.
- 비밀정보·인증서·지표·로그와 복구 구성을 서비스 코드와 분리해 관리합니다.

따라서 이 구조는 “서버 한 대에 올린 웹앱”보다 **요청 처리·데이터·배포·복구를 Git 중심으로 연결한 서비스 운영 환경**으로 설명합니다.

## 2. 30초 소개

### 30초 버전

실험플랫폼 서비스는 클라우드 서버에서 실행됩니다. 운영자와 연동 서비스의 요청은 안전한 접속 처리와 요청 분배를 거쳐 실험플랫폼으로 전달되고, 서비스는 실험 DB와 활동 DB를 사용해 사용자별 결과를 결정합니다. 코드가 바뀌면 자동 검사 후 새 버전이 만들어져 이미지 저장소에 보관되고, 운영 저장소의 버전 정보가 갱신되면 배포 도구가 새 버전을 자동 반영합니다. 비밀정보와 인증서, 지표와 로그, 복구 절차도 같은 운영 체계에서 관리합니다.

### 더 짧게 · 10초 버전

요청 처리부터 데이터 연결, 자동 배포와 복구까지 Git을 기준으로 이어지는 실험플랫폼 운영 환경입니다.

## 3. 아키텍처 흐름

```text
운영자 · 연동 서비스
          │ HTTPS 요청
          ▼
외부 요청 입구 → HTTPS 처리와 요청 분배
          │
          ▼
실험플랫폼 서비스
  ├── 실험 DB: 실험 설정 · 노출 기록
  ├── 활동 DB: 대상자 판단 데이터
  └── 파일 저장소: 첨부 · 파일

코드 변경
  → 자동 검사
  → 실행 이미지 저장
  → 운영 저장소의 버전 갱신
  → 배포 도구가 변경 감지
  → 실험플랫폼 서비스 새 버전 반영

비밀정보 · 인증서 ── 보호 ──▶ 실험플랫폼 서비스
지표 · 로그 ◀──────── 관찰 ─── 실험플랫폼 서비스
```

외부 요청 → 실험플랫폼 서비스 → 데이터 저장소로 이어지는 실행 흐름과, 코드 변경 → 검사·이미지 → 운영 저장소 → 자동 배포로 이어지는 변경 흐름을 함께 보여줍니다.

### 각 구성요소를 한마디로

| 구성요소 | 역할 | 부스용 표현 |
|---|---|---|
| 외부 요청 입구 | 인터넷 요청을 실행 환경으로 전달 | “사용자 요청이 들어오는 첫 관문입니다.” |
| HTTPS·요청 분배 | 안전한 접속과 서비스 요청 전달 | “요청을 안전하게 받고 실험플랫폼으로 보냅니다.” |
| 실험플랫폼 서비스 | 실험 설정과 사용자별 경험 결정 | “실험 화면과 판단 기능이 실제로 실행되는 서비스입니다.” |
| D1·R2 | 실험 기록·대상 데이터·파일 보관 | “실험에 필요한 데이터가 저장되는 곳입니다.” |
| CI·이미지 저장소 | 자동 검사와 실행 버전 보관 | “검증된 코드를 실행 가능한 버전으로 만듭니다.” |
| GitOps 배포 | 운영 버전 자동 반영과 롤백 | “Git에 기록된 버전을 운영 환경에 맞춥니다.” |
| 보안·관찰 | 비밀정보·인증서·지표·로그 관리 | “서비스를 안전하게 운영하고 문제를 찾게 합니다.” |
