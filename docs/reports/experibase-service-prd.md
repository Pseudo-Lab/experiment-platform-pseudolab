# ExperiBase 서비스 PRD와 구현 대조

2026-10-31 최신 결정: 사용자가 A 개선안을 승인하고 “이대로 반영해줘 운영배포까지 main커밋”을 요청했다. 소개·로그인을 실제 앱에 반영했으며, 기존 커밋·푸시·배포 금지 지시는 이 범위에서 대체됐다. 관리 화면 구현은 범위에 포함하지 않는다. 아래 선택 전 기록은 탐색 이력이며 최신 구현·검증 상태는 문서 마지막 절과 핸드오프를 따른다.

## 1. 서비스 정의

**ExperiBase는 서비스의 서로 다른 화면·기능을 사용자에게 제공하고, 행동 데이터를 비교해 다음 개선 결정을 돕는 오픈소스 실험 플랫폼입니다.**

작은 개발·분석 팀이 ‘왜 바꾸는지 → 어떤 버전을 제공하는지 → 무엇을 기록하는지 → 결과를 어떻게 해석하는지’를 연결하도록 돕습니다. 현재 적용 맥락은 가짜연구소 서비스이며, 다른 서비스에도 SDK/API로 연동할 수 있는 방향을 지향합니다. 범용 서비스 지향과 누구나 가입 가능한 운영 서비스 제공은 구분합니다.

이 문서는 분산된 기획·설계 문서와 코드를 대조한 제품 검토 진입점입니다. `active`는 이 검토 기록을 유지한다는 뜻이며, 아래 제안을 모두 승인하거나 개발 완료로 선언하는 뜻이 아닙니다. 기존 API·보안 계약을 대체하지 않습니다.

### 근거와 확인 범위

- 코드 기준: main `c993547` 및 이 커밋에서 분리한 `feat/service-intro`의 로컬 소개 UI.
- 관련 자료: README, 문서 인덱스·결정 로그, 기반 계획, 대시보드 계획, Feature Flag·SDK/API·외부 서비스 협업 계획, 최근 UI·보안 핸드오프, SDK 구현과 안내 문서.
- 별도 작업공간의 9월 사전 조사와 10월 UI 연구도 참고했습니다. 외부 제품의 최신 기능이나 수치는 이번에 재검증하지 않았으며, PRD 요구사항의 근거로 그대로 채택하지 않습니다.
- PR 조회 시 #26 Google OIDC/프로젝트 접근 제어는 미병합입니다. PR #12도 열려 있지만, 이를 근거로 main에 관리자 인증이 없다고 해석하지 않습니다.
- 이번 검토에서는 운영 DB·실제 고객 이벤트·배포 이미지 일치를 재검증하지 않았습니다. ‘main 구현’과 ‘운영 검증 완료’를 구분합니다. Notion 전체나 모든 과거 아카이브의 전수 검토는 아닙니다.

## 2. 누구의 어떤 문제를 해결하나요?

| 사용자 관점 | 해야 하는 일 | 현재 겪을 수 있는 문제 | 필요한 결과 |
| --- | --- | --- | --- |
| 서비스를 만드는 개발자 | 버전 분기와 이벤트 수집 연동 | 어떤 키·API·이벤트를 써야 하는지 불명확 | 예제와 실제 계약이 일치하고 첫 이벤트까지 확인 |
| 실험을 기획·분석하는 팀원 | 가설·지표·대상·기간 정의 | 설정값은 있으나 무엇이 필수인지, 무엇을 비교하는지 혼동 | 설계와 수집·결과를 연결해 설명 가능 |
| 기능 운영 담당자 | 시작·중단·점진 공개와 후속 결정 | 설정 완료를 수집 정상 또는 효과 검증으로 오인 | 운영 상태와 데이터 근거를 구분하고 결정을 기록 |
| 처음 방문한 사람 | 서비스의 용도와 이용 조건 파악 | 관리 화면만 보면 제품의 역할을 이해하기 어려움 | 짧은 소개를 읽고 실제 가능한 다음 단계로 이동 |

위 구분은 사용자 과업을 정리한 것입니다. 별도 회원 역할이나 RBAC가 모두 구현됐다는 의미는 아닙니다.

### 제품 범위에 관한 기존 결정

1. 실험 플랫폼은 실험 설계·연동·수집 확인·분석·결정에 집중합니다. 커뮤니티 전체 현황 대시보드는 사용자 결정에 따라 가짜연구소 홈페이지 쪽 작업으로 분리합니다. 남아 있는 GitHub/Discord 경로의 삭제는 이번 요구사항이 아닙니다.
2. 실제 서비스의 화면·라우트·배포는 해당 서비스가 소유합니다. 플랫폼 설정만으로 임의의 화면을 새로 만들거나 모든 행동을 자동 수집하지 않습니다.
3. 12기 회고는 무작위 대조군이 없는 준실험입니다. 연동·노출·완료 흐름의 검증을 A/B 인과 효과의 증명으로 소개하지 않습니다.
4. 팀 활동·회고·개발 이야기는 별도 팀 페이지에서 다룹니다. 서비스 소개와 팀 소개의 목적을 구분합니다.

## 5. 서비스 소개는 어디에 두나요?

| 위치 | 역할과 내용 | 판단 근거 |
| --- | --- | --- |
| 로그인 화면 | 한 문장 정의, 짧은 이용 맥락, ‘서비스 살펴보기’ | 처음 온 사람이 로그인 전 제품을 이해하면서 기존 로그인도 바로 사용 |
| 공개 `/about` | 사용 상황 3개, 이용 흐름 4단계, 현재 접근 조건 | 설명을 더 읽고 싶은 사람이 선택해서 열 수 있음 |
| 관리 화면 하단 링크 | 소개를 다시 찾는 진입점 | 핵심 실험 메뉴와 경쟁하지 않음 |
| 별도 팀 페이지 | 팀 활동·학습·개발 이야기 | 제품 사용 설명에 팀 연혁을 반복하지 않음 |

현재 루트 `/`는 기존 진입 동작을 유지합니다. 대형 랜딩페이지, 가격표, 고객 로고, 공개 가입, 추가 영업 CTA는 이번 범위에 없습니다. `/about` 구현은 인증 상태 복원 실패 중에도 소개를 읽도록 하되 프로젝트·관리 데이터 API를 호출하지 않습니다.

소개 문구는 ‘버전 배정·행동 수집·결과 확인을 돕는다’는 수준으로 유지합니다. ‘SDK 설치만으로 실제 노출과 모든 전환을 자동 수집’, ‘어떤 실험이든 정확한 승자를 자동 판정’, ‘GA/GTM 또는 BigQuery가 기본 연결됨’은 약속하지 않습니다. GA/GTM 전환과 BigQuery 접근 업무는 별도 서비스 데이터 작업이었으며 ExperiBase의 범용 기본 기능으로 전환된 근거가 없습니다.

로컬 화면·테스트·배치 근거: [서비스 소개 핸드오프](handoffs/2026-10-31-service-intro.md).

### 판단에 필요한 세 개념

- **활성화(Activation)**: 로그인 성공보다 ‘사용자가 첫 가치를 확인한 순간’입니다. 여기서는 자신의 서비스에서 온 첫 실험 이벤트를 확인하는 단계로 제안합니다. 현재 측정되는 KPI라는 뜻은 아닙니다.
- **점진적 공개(Progressive disclosure)**: 처음에는 필요한 정보만 보여주고 자세한 설정은 필요할 때 여는 방식입니다. 짧은 로그인 소개→상세 소개, 가설·지표→추가 설정에 적용합니다.
- **지표 계약(Metric contract)**: 같은 지표를 누구나 같은 방식으로 계산하도록 분자·분모·대상·기간을 약속하는 것입니다. 주요 지표에 이벤트명을 넣는 것만으로 이 계약이 완성되지는 않습니다.

### 수용 기준 — 구현과 후속 제안 구분

- **E1 서비스 소개:** KO/EN 제품 정의·이용 조건·사용 상황·네 단계 흐름. 데스크톱은 정의와 흐름 요약을 나란히, 좁은 화면은 순서대로 표시. 실제 성과처럼 보이는 샘플 수치 없음.
- **E2 로그인:** 헤더에 브랜드/소개 진입, 언어와 테마 전환. 관리자 이용·연동 조건을 폼에 명시. 제출 중 안내·버튼 비활성, 인증 실패/접속 실패 구분과 입력 보존.
- **E3 첫 연동 · 후속 PRD:** 프로젝트 생성 성공과 목록 갱신 결과 구분. 성공 안내의 SDK 버튼은 대상 프로젝트가 목록에 있고 오류/로딩이 없을 때만 활성. 누르면 선택 후 기존 SDK 화면으로 이동.
- **E4 프로젝트 탐색 · 후속 PRD:** 조회 오류를 빈 목록으로 표현하지 않고 재시도를 제공. 기존 프로젝트도 ‘실험 관리 열기’와 ‘SDK 연동 안내’를 명시적 버튼으로 제공해 키보드로 접근 가능.
- **E5 경계:** 공개 소개에서 프로젝트/관리 데이터 요청 없음, 기존 관리자 인증·삭제 보호 유지. 최초 커밋·푸시·배포 금지는 10/31 후속 사용자 지시로 소개·로그인 범위에서 해제됐다. 브라우저는 로컬 API stub, 동작 회귀는 자동 테스트로 확인하며 운영 검증과 구분한다.

### 이후 구현 순서와 열린 판단

1. 소개·로그인(E1/E2)과 경계(E5)를 이번 코드 범위로 완성한다. 첫 연동·프로젝트 탐색(E3/E4)은 PRD 후속 요구사항으로 남긴다.
2. 실험 목록→설계→수집→결과→결정의 기존 화면을 위 과업 순서에 맞춰 정리한다. 현재 구현의 정보 순서와 상태를 재사용하되 전체 개편 완료로 표시하지 않는다.
3. Feature Flag·Placement·SDK의 고급 설정을 정렬한다. 키 계약·집계 범위의 수정은 별도 기능 검증을 동반한다.

전체 화면 목록과 상태 보드는 [인계 문서](handoffs/2026-10-31-service-intro.md)의 ‘전체 UI 검토 구성안’을 따른다. Figma 작업 대상은 `vgFUYOtBogHljPEBukNSyH`이며 호출 한도로 아직 실제 전체 시안을 배치하지 못했다. 코드 결과가 Figma에 동기화됐다고 간주하지 않는다. 공개 이용 대상·Google 가입 운영 시점·분석 계산 계약은 이번 시각 변경으로 확정하지 않는다.

### 제품 플랫폼의 시각 방향 — 사용자 피드백 반영

- 2026-10-31 사용자 피드백: “핵클, growthbook과 같이 뭔가 제품 플랫폼 느낌을 가져가고 싶은데.” 이 프로젝트의 소개·로그인 방향으로 기록한다. 특정 경쟁 제품의 색상·폰트·전체 기능을 채택한 뜻은 아니다.
- 공식 [핵클](https://hackle.io/en/)과 [GrowthBook](https://www.growthbook.io/)에서 제품 영역 구분과 제품 화면 중심 소개 방식을 참고했다. ExperiBase는 현재 제공 범위인 실험 설계·Feature Flags·수집/결정에 적용한다. 경쟁 제품의 고객 수·성과·자동화 기능·무료 가입을 가져오지 않는다.
- E1을 구체화: 소개 첫 화면에서 가치 제안과 제품 미리보기를 나란히 보여준다. 미리보기는 ‘설명용 예시’로 표시하고 실험 설계/기능 공개/결과·결정을 선택할 수 있다. 가설·버전·주요 지표, 비활성/0% 공개 예시, 아직 수집되지 않은 상태를 설명한다. 실제 관리 데이터 조회나 설정 변경은 없다.
- E2를 구체화: 로그인은 동일한 브랜드·제품 영역·테마를 이어 받는 작업 공간 진입 화면으로 구성한다. 좁은 화면에서는 보조 기능 목록을 줄여 로그인 폼 진입을 유지한다. 기존 관리자 인증과 서비스 소개 왕복은 보존한다.
- 이 변경은 기존 shadcn/ui, 테마 변수와 디자인 가이드의 indigo 강조를 사용한 로컬 구현이다. 사용자가 완성 시안의 구체 스타일을 채택한 상태는 아니며 다음 화면 검토에서 조정한다.

### 디자인 비교 3안 — 선택 전 제안

사용자의 “디자인 시안 3가지로 해서 보고해줘” 요청에 따라 소개·로그인 각 3안, 총 6개 화면을 별도 HTML 미리보기로 구성했다. 기존 앱 구현과 관리 화면은 변경하지 않았다. 아래 방향은 사용자 채택 전이며 E1/E2의 새 확정 기준이 아니다.

| 방향 | 서비스 소개 | 로그인 | 판단 |
| --- | --- | --- | --- |
| A · Clear Platform | 흰색·indigo, 중앙 가치 제안, 넓은 제품 화면 | 밝은 제품 소개 패널과 로그인 폼 | 추천. 제품 이해와 기존 UI 연속성에 유리하며 개성은 절제됨 |
| B · Build & Observe | navy·mint, 좌우 구성, 기술 연동 흐름 | 어두운 배경과 집중된 폼 | 개발자 도구 인상이 강하며 비개발자에게 기술적으로 보일 수 있음 |
| C · Learning Workspace | ivory·green, 팀의 질문·학습 중심, 부드러운 카드 | 여유 있는 설명과 폼 | 팀 접근성이 좋으며 기술 플랫폼의 인상은 상대적으로 약함 |

공통: 관리자 이용 조건·SDK/API 연동 필요·설명용 샘플 표시를 유지한다. 실제 인증/데이터 연동과 신규 기능은 포함하지 않는다. 비교 시안은 한국어로 작성했으며 실제 앱에 채택할 때는 기존 KO/EN·테마·인증·접근성 요구를 유지해야 한다. 현재 밝은 A/C와 어두운 B는 서로 다른 시각 방향이며 각각의 light/dark 구현을 완료했다는 뜻이 아니다.

검토 링크: [3안 비교](https://agent-server.tail03ec4e.ts.net:9449/design-review). Tailnet 연결이 필요하며 상단에서 방향·소개/로그인·모바일을 전환한다. Figma 대상 파일은 동일하지만 Starter 도구 호출 한도로 이번 3안을 저장하지 못했다.

### A안 발전 방향 4개 — 사용자 선호 반영

- 사용자 피드백: “A시안이 제일 나은데 … 해당 시안을 기준으로 베리에이션 4개.” A를 다음 탐색의 기준으로 채택했다. 개별 색상·서체·간격의 최종 승인을 뜻하지 않는다. 기존 B/C를 확장하지 않고 A의 밝은 제품 중심 방향 안에서 배치와 밀도를 비교한다.
- 검토 순서: 사용자가 HTML 또는 이미지로 먼저 보고 선택한 뒤 Figma로 이동하도록 요청했다. 이번에는 Figma 도구를 호출하거나 파일을 수정하지 않았다.
- 공통: 같은 제품 정의·헤드라인·관리자 이용 조건·샘플 실험을 사용한다. 각 방향의 소개·로그인 2개씩 총 8개 화면이다. 비교용 한국어 HTML이며 실제 앱의 KO/EN·light/dark·인증 구현을 대체하지 않는다.

| 제안 | 소개 화면의 차이 | 로그인 구성 | 선택 기준 |
| --- | --- | --- | --- |
| A1 · Open Canvas | 큰 중앙 제목, 넓은 여백, 연한 indigo 배경 위 대형 제품 화면 | 제품 설명 패널과 폼을 나란히 | 기존 A의 인상을 가장 충실히 발전. 제품 세부는 스크롤 후 확인 |
| A2 · Product Balance | 왼쪽 설명과 오른쪽 제품, 연동 흐름을 한 화면에 | 설명·제품 예시와 로그인 폼 | 제품 이해 속도를 우선할 때 추천. 첫 화면의 정보량은 증가 |
| A3 · Modular Workspace | 중앙 제목 아래 실험 화면과 기능 공개·수집 카드 | 중앙에 집중한 폼 | 플랫폼 범위를 구체적으로 표현. 여러 카드로 시선이 분산될 수 있음 |
| A4 · Essential Platform | 큰 좌측 제목, 우측 설명, 얇은 선과 넓은 제품 화면 | 구획선으로 설명과 폼 분리 | 단정한 인상. 원안보다 차분하고 건조하게 느낄 수 있음 |

### Gemini 독립 시안 검토와 A 개선안 — 선택 전

사용자가 Gemini에도 시안 3개를 요청해 참고한 뒤 도움이 되는 부분을 반영하도록 지시했다. 별도 산출물 디렉터리에서 `agy`의 **Gemini 4 Argon (High)** 모델을 명시해 실행했다. 기존 Gemini CLI는 `UNSUPPORTED_CLIENT` 인증 오류로 실패했으며, 실제 성공 결과는 Antigravity 경로다. A 원안의 소개/로그인 이미지와 제품 범위·관리자 이용 조건을 전달했다. 이 요청은 다른 모델의 이름을 Gemini로 붙인 작업이 아니다.

| Gemini 제안 | 유용한 점 | A 개선안에 반영한 범위 |
| --- | --- | --- |
| G1 · 정제된 워크스페이스 | 가설/기준안/비교안/지표의 시각적 구분, 기능별 미니 예시, 로그인 내 제품 맥락 | 가설 강조와 A/B 카드, 샘플 표시, 세 가지 기능의 작은 예시, 로그인 좌측의 간결한 실험 예시 |
| G2 · 모듈형 도크 | 실험/플래그/결정의 역할을 별도 영역으로 설명 | 플래그와 결정의 구분은 하단 설명에 활용. 모눈 배경과 첫 화면 다중 패널은 채택하지 않음 |
| G3 · 구조적 블루프린트 | 설정/연동/확인/결정 단계의 구분 | 원안의 한 줄 흐름을 네 단계의 짧은 설명으로 발전. 명세서형 화면과 어두운 바는 채택하지 않음 |

- A의 흰 배경·indigo·중앙 제목·넓은 단일 제품 화면을 유지한 별도 **A 개선안**을 만들었다. 원안과 개선안은 같은 HTML에서 전환 가능하다. 기존 원안 파일과 앱 코드는 보존했다. 개선안을 사용자가 채택한 상태는 아니다.
- Gemini 결과 검토 중 모바일 toolbar/header 넘침, 공개 0% 막대의 4% 채움, 수집 이력으로 누락 여부를 보장하는 듯한 문구, 플래그 비활성/0%가 운영 영향을 차단한다는 과도한 문구를 발견했다. 전달용 Gemini 검토본에서 수정했다. 불필요한 미제공 기능 나열도 줄였다. 수정 전 원본을 별도로 보존했다.
- 검토 링크: [Gemini 3안](https://agent-server.tail03ec4e.ts.net:9449/gemini-proposals), [A 원안 / 개선안](https://agent-server.tail03ec4e.ts.net:9449/design-review-refined). 소개·로그인과 모바일을 전환할 수 있다. 실제 인증과 Figma 반영은 포함하지 않는다.
- 산출물: `/home/ubuntu/.codex/visualizations/2026/10/30/01a18dcf-2898-70d3-b21d-8e592f442f60/experibase-gemini-review/`. `gemini-original.html`은 모델 원본, `gemini-reviewed.html`은 Codex 검토본, `refined.html`은 원안/개선안 비교다. 한국어 검토용이며 실제 앱 채택 시 기존 KO/EN·테마·인증 계약을 유지한다.
- 보조 도구 평가: 독립적인 정보 구조 아이디어를 얻는 데 도움이 됐다. 생성은 약 7분이 걸렸고 반응형·수치 표현·제품 문구 수정이 필요했다. 그대로 적용하기보다 검토 가능한 디자인 초안으로 활용하는 편이 적합했다.

### A 개선안 확정 및 실제 앱 반영
